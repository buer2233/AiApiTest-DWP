# project-info/UI/AGENTS.md

本目录是固定 loop 第 3 阶段：UI 原型图设计阶段。进入本目录工作前，必须先遵守根目录 `AGENTS.md` 和 `project-info/AGENTS.md`，再遵守本文件。

## 阶段目标

- 默认依据 `project-info/test_case/` 的详细功能测试用例，输出 UI 原型图和交互说明。
- 如果 `project-info/demand/` 的需求说明书已冻结角色、页面目标、核心字段、状态流转、权限边界和验收口径，可以与功能测试用例阶段并行输出第一版 UI 原型。
- 原型要能指导 `front-end/` 编写 Playwright 自然语言 UI 自动化测试和 Vue 页面实现。
- 本目录只放 UI 原型资料、交互说明和原型提示词，不放前端源码。
- UI 阶段评估为 `N/A` 时，本目录仍需输出同名 UI 适用性说明，记录不适用原因；涉及既有页面时引用既有视觉基线，无需伪造原型、区域拆解或映射。

## 设计方法与 Skill 选择

- 先依据冻结需求、功能测试用例、API 契约和 `DESIGN-claude.md` 确定页面目标、用户路径、信息层级、状态和交互，再决定视觉产物形式。
- 当前会话可用且任务匹配时，可使用 `ui-ux-pro-max` 辅助 UI/UX 决策、`design-system` 辅助 token 与组件规范、`imagegen` 辅助位图原型；不设置全局强制组合。
- Skill 只生成或校验候选输入，不能替代字段追溯、区域语义拆解、可访问性、响应式、异常状态、覆盖校准和主人已冻结的验收口径。
- Skill 不可用时使用现有设计稿、受控浏览器渲染或其他可追溯方式完成适用产物；只有替代方案会实质影响验收时才按熔断协议上报。

## 文件命名

- 同一需求必须沿用需求阶段的名称，仅后缀不同。
- 推荐格式：`需求名-UI原型.md`、`需求名-页面交互说明.md`。
- 原型图文件使用清晰英文或拼音命名，例如 `module-pass-rate-page.png`、`failure-cases-dialog.png`。
- Figma 导出的原型图或 Codex `imagegen` 生成的原型图片必须与同一需求同名归档，例如 `需求名-dashboard-figma.png`、`需求名-failure-dialog-imagegen.png`。
- 需要多方案比较时，候选图必须按生成顺序编号归档，例如 `需求名-candidate-01-imagegen.png`；候选数量由设计不确定性和风险决定，不设固定张数。
- 定稿可使用 `需求名-selected-figma.png`、`需求名-selected-imagegen.png` 或按页面拆分命名，并在同名原型说明中记录所依据的候选编号、选择标准和偏差。

## 视觉候选与定稿流程

- 新增页面或实质改变视觉、信息架构、用户路径的需求必须形成可执行高保真视觉产物；仅调整既有页面的局部文案、校验或非视觉行为时，可引用现有视觉基线并记录 UI 阶段 `N/A + 理由`。
- 是否生成多份候选图由设计不确定性、风险和冻结需求决定。需要比较时，各候选必须基于同一份需求、测试用例和 API 契约，不得为了视觉差异改变功能范围、字段、权限、状态流转或验收口径。
- 候选差异应服务真实决策，例如信息密度、导航结构、筛选布局、表格/详情组织、状态反馈或操作路径；不得只做颜色、装饰或无意义构图变化。
- 生成候选前在同名 UI 原型说明中记录输入来源、设计约束、候选差异目标和必要提示词；生成后记录产物路径、适用页面/状态、优点、风险和人工校准结论。
- 冻结规格已给出清晰选择标准且候选不改变关键用户路径时，agent 可按标准自主定稿并记录理由；候选涉及权限、关键操作路径或验收口径变化时，必须熔断交给主人裁决。
- Figma、`imagegen`、受控浏览器渲染或仓库既有设计工具均可作为视觉产物来源。工具选择不改变定稿必须覆盖核心 frame、弹窗、表格、筛选、加载态、空状态、错误态、权限态、响应式断点和关键反馈的要求。
- 定稿后必须导出可归档图片并记录来源、页面/frame 范围、导出路径、版本时间和相对候选的偏差。工具不可用但替代产物仍满足验收时无需增加主人中途审批。

## 复合原型图区域语义拆解

候选图、Figma 截图或主人标注图如果同时展示多个页面、多个状态、说明文字、红框箭头、点击后页面或登录后页面，UI 原型说明必须新增“区域语义拆解表”。该表是前端开发的硬输入，不得省略。

区域语义拆解表必须至少包含以下字段：

| 字段 | 说明 |
| --- | --- |
| 区域编号 | 使用 `R1`、`R2`、`R3` 这类稳定编号，后续 RTM 和前端实现沿用 |
| 图片位置 | 用自然语言描述位置，如“左上登录卡片”“中间说明轨”“右上注册面板”“底部深色受保护预览” |
| 区域类型 | `产品页面`、`弹窗/抽屉`、`点击后路由`、`登录后页面`、`状态示例`、`设计标注层`、`不实现说明` |
| 是否进入前端 | 只能填 `是` 或 `否` |
| 前端落点 | Vue route、组件、弹窗、状态名或“不进入 DOM” |
| 触发条件 | 页面初始可见、点击某按钮、登录成功后、无权限访问、接口返回错误等 |
| 禁止项 | 明确哪些同图区域不能同屏出现，哪些标注文字不能进入产品 UI |

以登录/注册复合图为例：

- 左上区域如果是登录界面，应标为 `当前登录路由初始可见`。
- 中间身份说明如果只是设计解释，应标为 `设计标注层 / 不进入前端 DOM`。
- 右上注册界面如果是“没有账号，使用邀请码注册”之后出现，应标为 `点击后独立注册路由或弹窗`，不得和登录初始页同屏展示。
- 底部深色页面如果代表登录后用例详情页，应标为 `登录后受保护页面`，不得出现在登录页首屏。

原型说明必须在“前端实现映射”小节中写清：每个区域对应的页面、路由、组件和 Playwright 验收点。前端开发如果发现 UI 原型没有区域语义拆解，必须暂停并回到 UI 阶段补齐，不得自行按整图复刻。

## 强制设计风格基线

- UI 方案必须严格遵守仓库根目录 `DESIGN-claude.md` 中定义的前端设计风格和前端样式风格，不再仅以外部链接或口头描述作为依据。
- 原型说明必须逐项引用或转写 `DESIGN-claude.md` 的关键约束：色彩 token、字体层级、间距、圆角、状态色、组件模式、响应式策略和 Do/Don't 禁止项。
- 任何新增页面、弹窗、表格、筛选器、详情面板和状态反馈，都必须说明如何落地 `DESIGN-claude.md` 的 warm cream canvas、coral primary、dark product surface、编辑式排版和克制层级。
- 如果需求确实需要偏离 `DESIGN-claude.md`，必须在同名 UI 原型说明中写明偏离项、原因、影响范围和主人确认记录；未确认前不得进入前端开发。

## 内容要求

- UI 原型应覆盖核心页面、弹窗、表格、筛选、分页、批量操作、状态标签、加载态、空状态、错误态和权限态。
- 说明应包含页面目标、主要组件、字段来源、用户操作、状态反馈、异常处理和响应式要求。
- 管理后台设计应安静、清晰、可扫描，优先满足高频操作效率，不做营销式落地页；视觉风格必须以 `DESIGN-claude.md` 为强制基线。
- 表格、筛选器、弹窗和详情面板仍以企业管理后台效率为先；Claude 风格只作为视觉语言，不允许演变为营销页、夸张卡片堆叠、大面积渐变或装饰性插画。
- 原型说明中必须给出核心色彩、字号层级、间距、圆角、状态色和主要组件示例，功能状态色必须与暖陶土品牌强调色区分，避免成功、失败、警告状态语义混淆。
- 可访问性必须覆盖语义化结构、键盘操作、焦点顺序与可见焦点、表单标签、错误关联、色彩对比，以及不能只靠颜色传达状态。
- 每个新增页面或实质视觉/交互变更的 UI 方案必须至少包含一种高保真视觉产物，例如 Figma 导出图片、`imagegen` 原型图片或受控浏览器高保真渲染；这类需求仅有 Markdown 文字说明不满足 UI 阶段完成标准。
- 使用 Figma 时，应在原型说明中记录 Figma 文件/页面名称、导出图片路径、核心 frame 覆盖范围和版本时间；不得提交私有访问 token 或不可公开的组织链接。
- 使用 Codex `imagegen` 时，应在本目录保留用于生成原型图片的提示词、生成图片路径、适用页面/状态和人工校准结论，确保后续前端实现可追溯。
- 失败用例界面必须体现 `失败` 和 `跳过` 两种可展示状态，以及二者对通过率计算的差异。
- 重试操作必须体现确认、提交中、成功、失败和报告入口。
- 并行输出的 UI 原型必须标注输入来源为需求说明书，并在功能测试用例完成后补做覆盖校准。
- 覆盖校准必须检查正常场景、异常场景、边界值、权限态、状态流转、加载/空/错误状态和容器化部署下的报告入口访问方式。
- 涉及 API 数据的页面必须标注字段来源、筛选参数、分页参数、状态枚举和错误反馈，不直接假设后端字段。
- 涉及复合原型图时，必须校准每个区域是否属于当前页面、点击后页面、登录后页面或设计说明层，避免前端把非当前区域误实现到同一屏。

## 与开发阶段的关系

- UI 阶段适用时，前端开发前必须能依据本目录原型写出可执行 Playwright UI 自动化测试。
- UI 阶段评估为 `N/A` 时，前端开发以同名 UI 适用性说明、功能测试用例和既有视觉基线作为 UI 输入。
- 如果开发中需要调整交互，应先更新 UI 原型和交互说明，再修改前端实现。
- UI 阶段适用时，前端开发启动前必须确认本目录 UI 原型已完成测试用例覆盖校准、复合图区域语义拆解，并且后端 API 契约已冻结；UI 阶段评估为 `N/A` 时则核对适用性说明和其他适用前置产物。

## 安全要求

- 不提交真实账号、密码、token、cookie、租户密钥、生产 URL 或敏感地址。
- 页面示例数据使用占位符或脱敏数据，不绑定不可迁移的业务常量。
