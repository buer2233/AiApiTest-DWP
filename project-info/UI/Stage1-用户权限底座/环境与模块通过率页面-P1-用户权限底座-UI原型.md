## 2. 设计目标

P1 的 UI 首屏不是营销页，而是平台权限入口。页面需要同时解决三件事：

1. 让已有用户快速登录，并明确 Cookie 登录态由后端写入。
2. 让受邀用户通过邀请码注册，理解角色来自邀请码而不是前端自选。
3. 让未登录用户看到受保护路由和 401 门禁关系，避免误以为直接访问 URL 可以进入平台。

选中图 5 `Access Split Gate` 的核心结构保留为正式方向：

- 左侧：登录表单。
- 中央：身份权限分流轨，展示管理人员和普通成员能力差异。
- 右侧：邀请码注册表单。
- 底部：深色受保护平台预览，展示 `authToken Cookie` 脱敏状态、菜单锁定和 401 门禁。

深色面板是本页面的签名元素，用来把“无权限不能通过 URL 进入平台”视觉化。

| 区域 | 内容 | 状态表达 |
| --- | --- | --- |
| 401 门禁 | 大号 `401`、盾牌锁图标、文案 `受保护路由` | `error #c64545` 用于 401 数字和未通过状态。 |
| 锁定菜单 | 概览、接口管理、用例管理、测试执行、报告中心、缺陷管理、系统设置 | 每项右侧展示锁图标；未登录时不可点击。 |

## 6. 交互流程

### 6.1 登录流程

1. 用户输入账号和密码。
2. 点击 `进入平台`。
3. 前端校验必填和长度。
4. 调用 `POST /api/v1/auth/login`。
5. 成功：后端 `Set-Cookie: authToken=...; HttpOnly; SameSite=Lax; Path=/`，前端跳转受保护布局。
6. 失败：表单上方显示错误摘要，密码字段下方显示恢复提示，按钮恢复可点击。

### 6.2 注册流程

1. 用户输入邀请码、账号、密码和确认密码。
2. 点击 `创建账号`。
3. 前端校验邀请码非空、账号长度、密码复杂度、两次密码一致。
4. 调用 `POST /api/v1/auth/register`。
5. 成功：展示注册成功态，说明 `注册成功，请返回登录后进入平台`。
6. 失败：根据业务码展示字段级错误；用户名冲突不消耗邀请码。

### 6.3 路由守卫流程

1. 用户打开受保护 URL。
2. 前端调用 `GET /api/v1/auth/me`。
3. 200：恢复当前用户和权限摘要，进入目标页面。
4. 401：清理前端登录态，展示登录页或 401 受保护路由反馈。
5. 403：保留登录态，展示权限不足，不展示管理页面数据。

### 6.4 退出流程

1. 已登录用户点击退出。
2. 调用 `POST /api/v1/auth/logout`。
3. 204：清除 Cookie，跳转登录页，受保护预览回到锁定态。
4. 401：前端同样清理登录态并回登录页。

## 11. 安全与容器化检查

- UI 示例账号、密码、Cookie、token 均为测试或脱敏值，不使用主人提供的真实 Cookie 示例。
- 前端接口展示使用相对路径 `/api/v1/...`，不写宿主机固定端口或生产地址。
- 登录态只通过后端 HttpOnly Cookie 表达，前端原型不展示可读取的 token 明文。
- Figma 或 HTML 原型如需引用图片，必须使用仓库相对路径或公开无敏感资产。
- 移动端和桌面端均不得依赖本机绝对路径。
