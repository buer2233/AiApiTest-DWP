把当前系统做成可导入的技能

结论：嵌入式 Skill（自包含），非 Agent、非裸 AGENTS.md

三种方案对比

维度Skill（嵌入式）Agent标准 AI 流程（AGENTS.md）
触发方式关键词匹配（如「分析 r349084」）独立运行、持续监听靠项目通用指令
载体.workbuddy/skills/<name>/SKILL.md独立 Agent 定义就是 AGENTS.md

推荐理由

  • 原生扩展机制：WorkBuddy 自动加载 .workbuddy/skills/ 下的所有技能，无需额外安装。
  • 随仓库分发：把 Skill 放进测试框架 Git 仓库的 .workbuddy/，用户 clone 后打开 WorkBuddy 即自动可用。
  • 触发精准：description 字段控制触发词，说「分析 r349084」才激活，说「帮我写请假流程」不误触发。

Evals 设计（参考 E10 api-test-dwp）

svn-impact 必须由 skill-creator 创建与维护，不得手改 SKILL.md 后不登记；并强制配套两层 eval：

层级文件评估什么是否调模型
触发层trigger_eval_set.jsonquery 是否触发 svn-impact（正例/负例）是
工作流契约层workflow_eval_set.json触发后是否正确分流、读必读文档、产预期交付物、无禁止副作用否

触发层正例分支须覆盖：阶段 A（标准 / skip-update）、阶段 B（新建封装 / 复用）、阶段 C（复测）、快速测试（复用 / 换环境）、报告分析（有失败 / 无失败）、接口覆盖校验、用例选取（按功能关键词 / 按 revision）；负例须覆盖：HEAD/范围/多版本、UI 自动化、前端代码、纯单元测试、数据库迁移、解释性提问、报告样式。Windows runner 需兼容 select() 限制，支持 checkpoint 续跑，超时/无信号标 INCONCLUSIVE 不折算为不触发。

2a

接口覆盖校验：URL 是否已封装

结论：参考 E10，脚本扫 URL 入 sqlite3，关系型关键字查询

当前问题

inventory.py 用正则 url\s*=\s*['"]([^'"]+)['"] 扫 URL 字面量，结果只写 output/_inventory.json，不持久化、不跨 revision 复用、不抽 HTTP method/docstring/注释元数据，查询靠 JSON 字符串匹配。对「URL 是否已封装」这类确定性问题，mcp 图谱查询属于杀鸡用牛刀。

E9 专用简化扫描器（参考 E10 架构，规则按 E9 模板规范大幅简化）

E9 接口方法由 AI 按 api-test-E9/docs/api_test_case_spec.md 模板规范编写，格式固定（url 单独提取为变量、self.post/get 统一调用、三行元数据注释），扫描规则比 E10 简单很多，不照搬 E10 规则集：

维度E10（历史存量，写法多样）E9（强制模板，规则简化）
URL 提取4 条规则（quoted_http_url / concat_http_url_path / url_assignment_path_literal / url_assignment_format_path_bare_query）1 条：url\s*=\s*['"](/[^'"]+)['"]，限定 / 开头绝对路径
HTTP method3 条（requests.request / requests.get|post / .send_msg）1 条：self\.(get|post|put|delete)\s*\(，BaseAPI 统一入口
元数据注释# Author / # Create Date / # Update Date# Author / # Create Date / # IsAI（标识 AI 编写，非 Update Date）
docstring 描述抽 desc: 前缀行抽 docstring 首行非空行
  • 扫描器位置：api-test-E9/tools/scan_page_api.py；索引库 api-test-E9/tools/page_api_index.sqlite3；DB 工具 api-test-E9/skill_utils/api_index_db.py（参考 E10 api-test-dwp 的 skill_utils/ 但规则集重写）。
  • 双模式：空库走全量替换（id 从 1 起）；非空库走增量追加，(api_url, http_method) 做存在性 diff。
  • AST 优于正则：拿 ClassDef→FunctionDef 结构稳定挂「URL 属于哪个类的哪个方法」。E9 虽格式固定纯正则也能稳定，AST 仍用于方法归属与 @allure.step 装饰器提取。
  • UTF-8 强制：sys.stdout.reconfigure 避免 Windows cp936 崩溃。

E9 适配：表结构与覆盖判定

表字段说明
api_methods（主表）id, api_url, http_method, api_name, api_desc, class_name, class_bases, file, line, author, create_date, is_ai, mtime(api_url, http_method) 唯一；api_url 归一化（去 query、补前导 /、去尾 /）；is_ai 取自 # IsAI: 注释
index_metadatagenerated_at, repo_root, scanner_version, scanned_files, total_methods, unique_paths, scan_mode扫描元信息
覆盖判定（阶段 A 产出 endpoints 后，对每个 endpoint）：
SELECT api_name, class_name, file, line, http_method
FROM api_methods
WHERE api_url = ? AND (http_method = ? OR http_method = '')
命中 → has_wrapper=true，复用封装；未命中 → 阶段 B 新建
  • 位置：api-test-E9/tools/page_api_index.sqlite3，随仓库版本管理。
  • output/_inventory.json 降级为给 AI 读的脱敏快照；判定走 sqlite3。
  • 刷新时机：阶段 B 写入封装后、阶段 C 复测后、独立 python -m svn_analyse inventory --refresh-index。
  • sqlite3 管 URL 字面量，mcp 管调用链与符号（见 2b），不互斥不重叠。
验收：阶段 A 报告的「已实现/未实现」判定可在 sqlite3 等值查询复现；增量扫描后 (api_url, http_method) 唯一无重复；扫描器不写绝对路径；Windows + 中文路径不崩。
2b

功能覆盖与快速选用例 + 生成新用例

结论：mcp 调用链 + revision mark + SVN 提交描述元数据

核心判断

用例的功能覆盖不能靠 URL 关键字。用例标题、步骤描述是自然语言；一个用例可能调用多个接口方法覆盖一个功能点；同一 URL 可被多个用例以不同断言覆盖。原方案「双索引交叉分析」只解决 URL 维度，功能维度必须走 mcp 调用链 + 用例语义元数据。

mcp 调用链反向查选用例

变更符号（来自 facts.json，如 WfForceOver）
  → 外部 MCP impact(version, WfForceOver) → 受影响 Action / HTTP 端点
  → 对每个受影响符号，在 E9 外部图谱反向查 callers
    → 命中的 test_xxx 即「已有用例覆盖该符号」
  → 结合 docstring 标题 + 步骤描述判定测试点
  → 输出：已覆盖测试点 + 未覆盖测试点（需新建用例）
  • MCP 初始化、同步和版本切换由外部 E9 MCP 服务负责，调用方不执行 mcp init/sync。
  • 调用方只保存 MCP URL、版本和认证材料引用，不保存 E9 图谱数据库或本地 MCP 运行时。
  • 阶段 B/C 只消费外部 MCP 的调用链结果，再与本地 sqlite3 用例索引关联。

关键新增：revision mark + SVN 提交描述作为选取/执行元数据

用例编辑提交时打 @pytest.mark.r349094，并备注 SVN 提交描述如 no.4952725 优化等保分保的功能。这两部分是选取与执行的关键：revision mark 回答「用例因哪个提交而生」，commit 描述回答「该提交改了什么功能」，从而支持「按功能关键词反查 revision → 按 mark 选例 → 执行」。

元数据来源本轮需求
revision mark用例文件内 @pytest.mark.r349094继续采集（已有 _MARK_RE），并入 sqlite3
SVN 提交描述svn log -r REV commit message新增采集，并入 sqlite3，与 mark 关联
用例标题测试函数 docstring 首行继续采集
关联表字段说明
revision_metarevision, commit_msg, commit_author, commit_date, functional_keywords, analyzed_at, report_pathcommit 描述与功能关键词，支持模糊匹配反查 revision
test_methodsid, test_name, file, marks, title, calls, line用例与 revision mark 关联

选取流程

用户: 跑一下等保分保相关的用例
  → revision_meta.commit_msg LIKE '%等保分保%' → 命中 r349094
  → 用 mark r349094 查 test_methods → 用例清单
  → pytest -m r349094 执行

用户: r349094 改了什么，有没有用例覆盖
  → revision_meta 查 commit_msg
  → facts.json 查受影响符号
  → 外部 MCP callers 反查 E9 图谱 → 已有用例
  → sqlite3 test_methods 补 docstring 标题
  → 输出：已有 N 个用例覆盖 X 测试点；未覆盖 Y 测试点

与 2a 的边界

  • 2a 回答「URL 有没有封装」→ 阶段 B 是否新建 page_api 方法。
  • 2b 回答「功能点有没有用例覆盖」→ 阶段 B 是否新建 test_case 用例。
  • 两者在阶段 A 的 design.json 同时产出，互为补充。
验收：给定 commit 描述关键词能在 revision_meta 模糊查到 revision；给定 revision 能用 mark 在 test_methods 查到全部关联用例；mcp callers 反查结果与 mark 关联结果一致（差异需说明）。

测试报告 + 结果分析

需求 5 · 一期
5

并行分析失败原因并回写 Allure

结论：最多 10 个只读子代理；主会话是唯一校验与写入者

设计思路

先冻结指定运行的 allure-results/*-result.json 清单和 SHA-256，再按规范化失败指纹去重、分片。主会话按 min(10, 唯一失败数, 可用并发) 调度子代理；没有失败时不启动子代理。

每个子代理只读脱敏、截断的输入 JSON，不能读配置、执行命令或写文件。所有输出由主会话校验后回写为受管 AI 分析 attachment，随后重新生成 Allure HTML。

规则分类器

pytest → 冻结 manifest（UUID + SHA-256 + 脱敏错误）
       → 按 fingerprint 去重，最多 10 个只读子代理
       → 主会话校验 schema、hash、分类和敏感信息
       → 原子替换 result.json，追加/替换一个 AI 分析附件
       → allure generate → summary.json

分类：environment / credentials_config / dependency /
      test_data / test_code / product_defect / unknown

输出格式

=== 测试结果 ===
版本: r349084 | 总计: 5 | 通过: 4 | 失败: 1 | 唯一失败类型: 1

失败用例分析：
✗ test_force_over_removed_from_todo
  → 测试环境连接超时；先确认环境可访问且已部署目标版本。

Allure: 每条失败结果内可查看「AI 分析」附件

远端架构：知识图谱 / 用例远程化

需求 6 · 二期完成本地能力，远端部署验收归远端开发
6.1

两套图谱的远端能力与选型

结论：MCP 已有原生 stdio MCP；生产仍需企业网关与 SVN 更新作业

现有 E9 索引由 MCP 1.5.0 构建，已支持 mcp serve --mcp、sync 与 JSON 查询；因此不应从零开发查询型 MCP。其原生 MCP 是本地 stdio，不是带认证的远程 HTTP 服务。

codebase-memory-mcp 提供更广的 Java Hybrid LSP、语义检索和 15 个 MCP 工具，但同样只有 stdio transport，且 watcher/detect_changes 只支持 Git；它不能自行更新 SVN 工作副本。推荐保留 MCP 生产索引，另把替代引擎放入真实 E9 revision 的 PoC。

WorkBuddy → 企业 HTTPS MCP Gateway（认证 / ACL / 审计）
          → MCP 原生 MCP / SDK 查询池
          → 异步更新作业：锁 → svn update → graph sync → 验证 → 原子激活

只允许 request_refresh(repo_id, revision?)，禁止任意 shell、路径、SVN URL 和凭据参数。

输入模板与边界

  • 连续区间模板：分析 Revision r349181 到 Revision r349184，提交说明：no.4996246 解决了流程导入不会更新明细表配置的问题；区间语义始终是闭区间，但是否存在中间 revision 必须由读取 MCP 实际查询确认。
  • 显式集合模板：分析 Revision r349181、Revision r349184，提交说明：...；只分析用户列出的 revision，不推断中间编号，也不要求连续。
  • 快速测试模板：快速测试 Revision r349181 到 Revision r349184，提交说明：...；配置确认后按阶段 A → A+ 功能用例 → A++ 人工定稿 → B → C → 报告分析执行，任一门禁失败即停止后续写入。
  • 批次为 2–10 笔；区间数字跨度必须满足 B-A <= 10。读取 E9 信息 MCP 对 A、B 各查询左右最多 10 笔，合并去重后过滤闭区间；端点无效、缺少边界完整性证据、实际超过 10 笔或只找到一笔时提示修改。A=B 继续走单笔流程。
  • 批次必须提供总结性 batch_message；SVN 原始提交说明逐笔保留。单笔提示词继续兼容，不强制批次说明。

分析与产物

  • 每笔 revision 以完整分析 attempt 为单位最多重试 3 次，成功项不重复查询；最终失败记录真实 MCP 工具、阶段、attempt、错误和建议，任一关键事实缺失则阻断阶段 B。
  • 先写入 revisions/r<revision>/facts.json 与 design.json，再生成批次 aggregate_design，保留 source_revisions、resolver 证据和跨提交结论。部分报告不得进入阶段 B。
  • 批次目录为 output/batch_r349181_r349184/，包含批次 facts/design/reverse_lookup、报告和逐笔子目录。

状态与阶段 B 门禁

  • 区间 resolver 先对 A、B 各取左右最多 10 笔并校验边界完整性；状态不是 accepted 时停止，不进入阶段 A。
  • 逐 revision 的一次 attempt 覆盖全部关键查询，最多 3 次；失败后允许输出部分审计报告，但 stage_b_gate=false，不写接口代码。
  • 完整批次还必须完成 A+ 功能用例设计和 A++ 人工定稿，才能进入阶段 B；A=B 仍按单笔流程。

公共能力复用与 SKILL 方案

  • 单笔和批次共用一个 svn-impact SKILL；不新建第二个顶层批次 SKILL，避免 MCP 安全、功能用例、前置数据、阶段门禁和报告规则分叉。
  • 公共规则集中在 references/common-analysis-contract.md；功能用例设计统一遵守 references/functional-case-design.md，批次先合并影响模块再按同一规范设计。
  • 代码抽取公共 analysis_worker：单笔入口和批次逐 revision 都调用同一事实/反查逻辑；批次只新增 resolver、调度、聚合、batch_id 和多 mark。

Git 分支管理 Skill

需求 7 · 三期
7

自然语言切换 / 新建分支，默认从主分支拉取

结论：skill-creator 新增 git-branch 技能；默认分支可配置，新分支一律从主分支拉取

决策树

解析分支名（省略 → config.json 的 git.default_branch = master）
  ├─ git branch --list 已存在 → git checkout
  └─ 不存在 → 询问「是否从主分支新建」
       ├─ 确认 → git fetch → git checkout -b <name> <default_branch>
       └─ 否定 → 终止，零改动

安全边界

  • 切换 / 新建前 git status --porcelain 非空 → 先询问（stash / 放弃 / 取消），不静默丢弃。
  • 分支名按 git check-ref-format 校验，拒绝非法名。
  • 只读操作零副作用；切换失败回滚到原分支。
  • 只读 git 配置块，不读取 / 输出账号密码。

Evals 验收

  • 首批重点测 自然语言触发词的触发成功率（正例命中 / 负例不误触）。
  • 正向：切换已有分支；新建分支落 master；省略名回退默认；拒绝新建零改动。
  • 负向：非法分支名被拒；有未提交变更不得静默切换。
