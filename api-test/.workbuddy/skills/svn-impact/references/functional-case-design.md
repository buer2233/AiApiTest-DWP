# 功能测试用例设计规范

本文件定义 `svn-impact`「功能用例设计」阶段的方法论与产出格式。它是单笔 revision 和多笔批次共同遵守的唯一功能用例规范。功能用例从业务/黑盒视角覆盖变更行为，与阶段 B 的接口自动化用例（协议视角）互补：**功能用例是接口用例的母集**，阶段 B 从功能用例清单中抽取「需要接口回归」的条目落自动化，其余仅作回归指引。

单笔分析直接以该 revision 的 `facts/design/reverse_lookup` 为输入；批次分析先逐笔分析，再将联合影响面和来源 revision 合并后作为输入。批次不得为“多笔提交”另设简化版或平行版用例设计标准。

## 核心理念

- 以**专业测试人员**身份设计，站在最终用户与业务质量角度，而非「每个接口机械映射一条用例」。
- 功能用例描述「用户视角的操作 + 预期业务结果」，不绑定具体 HTTP 实现细节。
- 一条功能用例可跨越多个接口调用；一条接口可能只服务于某条功能用例的一个步骤。

## 覆盖维度

按本次变更的**实际行为**取舍（缺一不可地「考虑」，而非「硬凑」）：

| 维度 | 说明 | 典型设计方法 |
|------|------|-------------|
| 增（Create）| 新增数据/对象流程 | 正常创建 + 必填缺失/格式错误/重复创建 |
| 删（Delete）| 删除数据流程 | 正常删除 + 不存在/已被引用/越权删除 |
| 改（Update）| 修改数据流程 | 正常修改 + 字段边界/并发/越权修改 |
| 查（Read）| 查询/展示流程 | 正常查询 + 空结果/分页/过滤条件组合 |
| 边界值 | 输入域临界点 | 最小-1 / 最小 / 最大 / 最大+1 / 等价类邻值 |
| 等价类 | 输入域有效/无效划分 | 每个等价类至少一条代表用例 |
| 异常 | 非法输入与异常路径 | 类型错误/超长/特殊字符/依赖缺失/空数据 |
| 组合 | 多条件同时变化 | 判定表/成对组合，覆盖关键组合项 |
| 权限与状态 | 角色权限、状态流转 | 无权限/越权/跨状态非法流转/状态机覆盖 |
| **场景法（核心主流程）** | 先沿引用链归并受影响功能模块，再逐模块设计端到端主流程（详见下文专项） | 影响面透出路径 → 归并功能模块 → 每模块至少一条核心主流程 → 模块内补全功能 |
| **状态转换测试** | 对象状态机转换覆盖（详见下文专项） | 枚举状态与合法/非法转换 → 逐转换生成用例 |

> 纯查询变更不必硬凑增删改；后端签名/文案变更不必硬凑组合。**不得为凑数生成假阴性用例。**

## 专项一：场景法（核心主流程用例）

场景法沿**变更涉及方法的引用链**向前（向上游、向用户入口方向）追溯，定位到「该操作最初的前置业务步骤」，再从该前置步骤开始，按用户实际操作顺序梳理每一步调用的接口，形成一条完整端到端业务主流程。

### 影响面透出路径 → 功能模块归并（场景法前置，必须先做）

场景法不是「挑一条链路写一条」就完事，而是**先回答「本改动影响了哪些功能模块」，再对每个受影响模块分别设计核心主流程**。核心思想：**先覆盖全影响模块（横向），再针对每个模块覆盖全功能（纵向）**。

1. **透出路径归并**：把 `trace_path(inbound)` 得到的全部调用方（含 2 跳/3 跳传递的间接调用方），按「用户可感知的功能模块」归并，并为每个调用方确证「最终 HTTP 入口」（入口类 `@Path` + 方法 `@Path`）。同一模块的多个调用方合并为一条模块级透出路径。
2. **列出受影响模块清单**：产出一张「变更方法 → 调用方 → 功能模块 → 入口（URL）」的映射表，明确本次改动透出到哪几个模块。例如一笔后端 Biz 公共方法改动，可能同时透出到「邮件」「文件/文档」「流程表单」「表单建模」「立方体卡片」等多个模块。
3. **模块维度主流程覆盖**：对步骤 2 清单里的**每一个受影响模块**，各设计**至少一条**该模块的场景法核心主流程用例；若一个模块存在多条不同的业务入口/子功能透出路径（例如「邮件」模块同时透出「收件箱查收」「邮件正文」「邮件导出」「附件中心」多条子路径），则可**设计多条**核心主流程用例。所有受影响模块覆盖齐全后，才转入模块内的 CRUD/边界值/等价类/异常/组合/状态转换等功能覆盖。
4. **主用例的确定**：若覆盖了多个模块、多条主流程，则把「变更行为点最核心、用户入口最直接、且能完整走到变更分支」的那条标为本 revision 的**核心主用例（P0）**；其余各模块主流程按其业务重要性定 P0/P1，各模块内部的功能补充用例围绕该模块的主流程展开。
5. 每条场景法用例在「关联模块」字段标注其所属功能模块；「引用追溯路径」字段标注该模块的透出路径。

### 执行步骤

1. **取引用链**：用查询 MCP 的 `trace_path(function_name=<变更方法 qn>, direction="inbound", depth=3)` 拿到全部调用方；对每个调用方继续 `trace_path(inbound)` 向上游追溯，直到命中「不再向上有业务意义的前置入口」（通常是列表页 / 首页 / 登录后首屏）。
2. **定前置步骤**：选取一条「入口 URL 已确证、覆盖变更行为最完整」的链路作为主流程；记录**引用追溯路径**（变更方法 ← 中间调用方 ← ... ← 最前置入口）。
3. **数据准备先查询复用，缺失再造数**：主流程的目标查询/列表接口前必须有数据准备阶段。先通过对应业务接口查询当前测试环境是否已有满足条件的数据，命中则复用并把业务 ID 作为后续步骤锚点；只有查询为空或均不满足条件时，才按下方规则分析并新增前置数据。不得在已有可用数据时重复造数，也不得依赖环境中“碰巧存在”但未验证的数据。
4. **按序梳理接口**：从前置数据准备步骤起，按用户操作顺序列出每一步调用的接口（方法 + URL），并标注每步的**输入（请求参数）**与**输出断言点（关键返回字段/业务标志）**。
5. **落主用例**：把「查询复用/造数 → 查询 → 操作 → 断言」整条链写成一条「核心主用例」，字段含 `引用追溯路径 / 前置数据准备 / 步骤接口顺序 / 每步输入输出断言点`。**该用例作为本 revision 的核心主用例（P0），其余场景用例均作为补充用例。**

### 前置数据准备（先查询复用、缺失再造数 + 增量自动造数）

当目标接口前缺少已验证的数据准备步骤时，按以下判定补足「可落地的数据准备前置步骤」。**核心原则：先查询复用，缺失后能自动造的绝不要求人工；能拆多步就拆多步；确实造不出的部分才交给人工，且必须详述原因与所需数据内容。**

1. **现有数据查询（每次必做）**：对每个受影响模块，先通过已有接口方法按业务条件查询当前测试环境；校验状态、权限和必要字段，命中后直接复用并记录业务 ID。查询结果为空或不满足条件时，明确记录缺失对象，再进入造数分析。
2. **前置数据自动分析（每次必做，禁止一律要求人工）**：对每个受影响模块，通过 MCP 图谱（`search_graph` / `trace_path(outbound)` / `query_graph` / `get_code_snippet`）分析：
   - 查询/目标接口读哪些表、依赖哪些业务对象；
   - **哪个已有接口能新增/写入这些数据**（「新建/发送/保存/提交/导入」类入口）；
   - 该写入接口的入参（含密级/分类/状态等关键字段）与返回（业务 ID）。
   分析结论必须明确划分「可自动造数」与「需人工提供」两类，**凡是能通过已有前置接口造出的数据，必须直接写成具体可执行的步骤写入用例，禁止一律要求人工提供**。

3. **步骤拆分细化（禁止两步式）**：禁止把用例简化为「提供前置 + 接口验证」两步就结束。必须**最大限度拆解出可自动化的查询/复用或创建接口步骤**，形成完整的多步骤链路。典型链路形如：`查询并复用基础数据 → 关联业务数据 → 配置依赖项（密级/分类/权限）→ 触发目标接口 → 校验结果`；若查询无数据则替换为`创建基础数据 → ...`。每一步必须写清：接口 URL、请求参数、返回取用字段（锚定到下一步入参）。

4. **增量编写原则（能写多少写多少）**：分析后即使确有部分前置数据无法查询复用或自动造出（如「沙箱模式/工作秘密密级」是系统级配置、密级越权校验会拒绝越级造数、或依赖流程模板等复杂对象），也**必须先把所有能自动调用的查询、复用和创建接口全部写成具体步骤**，一直写到确实写不出的位置，再按 `functional-to-api-test/references/test-data-reuse.md` 的四项格式标注人工介入。不得因“有一步造不出”就放弃整条自动链路。

5. **可自动 / 人工介入两部分显式区分**：每个用例的前置步骤必须分两栏呈现——
   - **可自动生成部分**：每条都是可直接调用的接口步骤（URL / 参数 / 返回值锚点）；
   - **人工介入部分**：注明**具体数据内容**（要造出什么对象、什么密级/配置）、**来源**（哪个页面新建/哪个配置项）、**原因**（为什么接口造不出——系统级配置、密级越权校验、流程模板依赖等）。

6. **数据可用即查**：复用或自动造数完成后，目标查询步骤的断言点要以前置查询命中的业务 ID，或造数返回并经查询确认的业务 ID 为锚，形成「查询复用/造数 → 查询命中 → 操作 → 断言」的闭环，确保结果确定。

### 场景法用例字段（在通用字段基础上追加）

```text
- 关联模块：该主流程所属的功能模块（邮件 / 文件文档 / 流程表单 / 表单建模 / 立方体卡片 ...）
- 引用追溯路径：变更方法 → 中间调用方 → ... → 该模块最前置入口
- 前置数据准备：分「可自动生成部分」与「人工介入部分」两栏
    - 可自动生成部分：stepN 造数接口(URL) → 入参 → 返回值锚点（业务 ID）
    - 人工介入部分：所需数据内容 + 来源（哪个页面/配置）+ 原因（为何接口造不出）
- 接口调用顺序：step1 造数接口(URL) → step2 关联/配置接口(URL) → ... → 触发目标接口(URL)
- 每步断言点：stepN 输入参数 | 期望输出字段/标志
```

### 质量门槛

- **模块覆盖完整性**：受影响的功能模块清单必须逐一覆盖，每个模块至少一条场景法核心主流程用例；不能只挑入口最好确证的模块。漏覆盖某一受影响模块属于「场景法不全面」的缺陷。
- 每一步接口必须来自 MCP 反查证据（`trace_path` / `search_graph` / `get_code_snippet`），不得编造 URL 或参数。
- 追溯「向前」是沿 inbound 方向（谁调用我），不是 outbound（我依赖谁）；box 目标是找到**用户触点**而非底层 DB。
- 入口 URL 未确证时（如 command 分发入口），优先沿 `search_graph` 反查该 Command 所属的 HTTP Action（同包 `web/` 目录、或继承的 Action），确证后再落主流程；确证不到入口时降级为补充用例并标注「入口待复核」。
- **查询步骤前必须存在数据准备步骤**；先查询并复用现有数据，只有确认缺失后才造数；能拆多步则拆多步，确实无法完成时按四项失败格式标注人工介入（并说明数据内容/来源/原因）。
- 禁止「提供前置 + 接口验证」两步式敷衍；禁止因「存在一步造不出」就整条放弃自动链路。

## 专项二：状态转换测试（State Transition）

针对**变更涉及对象**建立状态机，枚举所有相关状态与合法转换路径，为每个状态转换生成用例，覆盖三类：合法转换、非法/被禁止的转换、边界条件。

### 状态机建模步骤

1. **识别对象与状态**：从变更涉及的对象（既可是业务实体，也可是「某一响应/判定的返回分支」）抽象出全部状态。若变更点是「提示文案选择」这类无实体的逻辑，则把**该方法的返回分支**建模为状态。
2. **枚举合法转换**：为每个「状态 × 触发事件」标出合法后置状态。
3. **枚举非法转换**：找出被禁止的跳转（如「已删除 → 有权限」「非沙箱 → 沙箱提示」），作为负向用例。
4. **标边界条件**：转换的临界输入（密级 key 为空/有效、切换沙箱的瞬间等）。

### 用例输出格式（统一）

```text
- 前置状态：<初始状态>
- 触发事件/接口：<触发转换的事件，或调用的接口>
- 期望后置状态：<转换后的状态>
```

每个状态转换一条用例，编号沿用 `FC-<seq>`，`类型` 标注 `状态转换`；额外补充一列 `转换合法性`（合法 / 非法 / 边界）。

## 用例字段约定（每条功能用例至少包含）

```text
- 编号：FC-<seq>（功能用例，与阶段 B 接口用例 AC-<seq> 区分）
- 标题：一句说清「什么场景下验证什么行为」
- 关联模块：所属功能模块（场景法必填；其余维度尽量标注）
- 类型：功能-增/删/改/查 | 边界值 | 等价类 | 异常 | 组合 | 权限 | 状态流转 | 场景法-核心主流程
- 优先级：P0（核心行为/回归必测）/ P1（重要分支）/ P2（次要/体验）
- 前置条件：登录身份、系统状态（如沙箱模式开关）；数据准备拆分为「可自动生成部分（具体接口步骤）」与「人工介入部分（数据内容/来源/原因）」
- 测试步骤：可执行的分步操作
- 测试数据：输入值（边界/等价类代表值），明确「为空/不存在」等特殊值
- 预期结果：可判定的业务结果（含提示文案、数据变化、跳转）
- 关联接口：需要接口回归时列出接口 URL 或封装名；纯界面/手动项留空
- 是否需自动化：auto（阶段 B 落为接口用例，且必须是一条 ≥2 个接口的前后调用链）/ manual（人工验证）/ contract（只读契约回归，允许单接口但要说明原因）
```

## 质量门槛

- 每条用例必须有**可判定的预期结果**，禁止「验证是否正常」「检查是否 OK」这类空洞表述。
- 来源可追溯：每条至少对应 `behavior_change` 的一个行为点，或一个影响面调用方。
- 不得编造接口、参数或返回结构：接口信息一律来自阶段 A 的 facts/reverse_lookup；图谱未覆盖的 JSP/SQL/前端标注「图谱未覆盖」。
- 敏感信息（账号、密码、token、内部 ID）不进清单，用角色名（管理员/普通成员）与占位数据代替。
- **`auto` 条目的接口调用链门槛**：标注 `auto` 的用例，其「接口调用顺序」必须是一条 ≥2 个接口、存在数据依赖（前步返回 ID 作为后步入参）的前后调用链；「单接口 + 拆分断言」不算多步骤，判据是实际发起的接口调用次数而非 `assert` 条数。无法凑出 ≥2 个接口链路的，降级为 `contract` 或 `manual`，并写明「无法形成跨接口链路」的客观原因。

## 产出与流转

- 产出文件：`E9_svn_analyse/output/r<rev>/functional_test_cases.md`（功能测试用例清单，Markdown 表格）。
- 产出后自动进入「人工审核」阶段；**未经人工确认定稿，不得进入阶段 B**。
- 阶段 B 从定稿清单筛选「是否需自动化 ≠ manual」的条目落接口自动化；`manual` 条目仅作回归指引，不生成 pytest 用例。
